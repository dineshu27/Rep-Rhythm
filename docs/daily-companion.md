# Daily companion

`/assistant` is a unified journal. Example: “I ate 150 g cooked rice and I did barbell bench press, 3 sets of 10 reps at 20 kg”. Clear completed reports automatically create actual food diary entries and completed workout history, not routines or planned meals. Automatic logging can be turned off. Receipts show dates, food matches, weights and sets and support Edit and Undo. Undo refuses to overwrite a record changed outside chat. Existing routines, active workouts, storage keys, backups and saved records are preserved. A report records equal reps/weight for each stated set; use separate exercise reports or the workout tracker for differing set values. No duration or workout calories are inferred.

Basic logging is deterministic local-catalogue matching through the server, not an LLM or arbitrary conversational intelligence. It requires explicit grams, sets, reps/time and kg (or explicit unweighted). Ambiguous exercise variants, preparation and missing quantities require review. Short follow-ups are resolved only for a single pending item. Questions, negated completions and future plans never auto-log. A step report replaces the selected day’s daily total, preserving other metrics. Do not combine separate activity increments as daily totals. A repeated identical message for the same date requires review before adding a duplicate. Recent receipt history is limited to 24 messages in sessionStorage for this tab; New conversation clears messages, not trackers. Actual tracker records remain in localStorage until cleared; export a Settings backup for safekeeping. Daily questions use a summary capped at the latest 20 foods/workouts, not a complete medical history.

Connected personal OpenAI/Anthropic keys use the existing encrypted, expiring HttpOnly key cookie. Provider sharing and billing consent are required. Extraction uses bounded structured output, no retry and no automatic paid fallback. Model interpretations that differ from deterministic catalogue/quantity checks require review. No real paid provider requests were used in automated release checks; adapters are covered with mocks. Existing planning and coaching remain at `/assistant?view=coach`. Basic logging is available without Supabase or any model key.

Home uses the profile timezone for dates, recorded nutrition and actual completed sessions for seven-day visuals. Empty days are unknown, not zero intake. Name editing updates only the profile name. Weather waits for an explicit city selection or browser geolocation permission. Approximate coordinates are rounded to two decimal places; the chosen location stays in localStorage under `fitai-weather-location-v1`. Forecast requests use fixed Open-Meteo endpoints with timeouts and caching. Weather is modelled current conditions and forecast, not a personal sensor. Errors remain unavailable rather than invented weather. Data attribution links to Open-Meteo under CC BY 4.0.

The public Open-Meteo free service is used for the current personal/noncommercial app with no advertisements or subscriptions. [Its terms](https://open-meteo.com/en/terms) require a commercial licence if that changes; do not enable subscriptions/ads or purchase a plan without authorization. City searches use [Open-Meteo Geocoding](https://open-meteo.com/en/docs/geocoding-api). Forecasts use [Open-Meteo Weather](https://open-meteo.com/en/docs).

## Watch data

`/connections` supports a local CSV with the exact header `date,steps`, ISO calendar dates and one whole daily total per date, up to 100,000 steps. Maximum file size 1 MB, maximum 3,660 daily rows. Duplicate dates, invalid values and future dates are rejected. Existing activity dates are skipped by default. Explicit replace updates only steps and preserves water, cardio and notes. Source files stay in the browser. This is a daily import, not live watch sync. Raw Apple Health XML, sleep, heart rate and activity-energy import are not implemented.

Apple Watch automatic sync needs a native iPhone companion app with [HealthKit capabilities and permission](https://developer.apple.com/documentation/healthkit/setting-up-healthkit); a Next.js browser site cannot request HealthKit access. No native companion exists in this repository. A next phase must implement the native app and an authenticated owner-scoped ingestion endpoint before claiming connected status.

Pixel Watch/Fitbit cloud sync uses Google Health API with developer registration and account OAuth. Other Android health records can use Health Connect from a native Android app. [Google’s migration guidance](https://developer.android.com/health-and-fitness/health-connect/migration/fit) describes these routes. No Google OAuth client, registered health integration or native Android bridge is configured here. Nothing is shown as connected or silently read. Setup needs the chosen watch/provider and account authorization through official screens; secrets must be configured through secure service settings, never chat. Daily CSV or manual/chat step totals work in the meantime.
